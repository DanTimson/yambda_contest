# Пакет экспериментов: тренды, артисты, объединения

Это следующий рабочий запуск вместо подробного учебного разбора отдельных блоков.
Скопируй два новых файла из `tools/` и тест в свой проект. Предыдущие файлы, в том числе
`tools/explore_yambda.py`, нужны, но **не заменяются**. Первый блок `eda_recency.py`
можно пропустить: его четыре варианта входят в этот расширенный пакет.

## Основной запуск

В существующем окружении с `requirements-eda.txt`:

```bash
python tools/benchmark_candidates.py \
  --data data/5b --users input/test_users.csv \
  --out eda_results/candidate_benchmark_v1
```

По умолчанию:

- воспроизводимая подвыборка **5000** пользователей из предоставленного списка, seed 42;
- четыре среза: за **120/90/60/30** дней до конца журнала;
- цель каждого среза — следующие **100 событий лайка**, не фиксированное окно;
- до **1000** кандидатов на источник, первые **100** — отдельная метрика выдачи;
- ограниченный каталог **200 000** исторически известных треков для источников артистов;
- до пяти любимых артистов, до 200 треков каждого, затем дедупликация и ограничение;
- агрегаты общей истории кешируются в `data/eda_cache`, чтобы не пересчитывать их при
  сравнении других бюджетов и персональных источников.

Подвыборка ограничивает обработку пользователей, но глобальные агрегаты всё равно
считаются по полному локальному файлу лайков. GPU не нужен. Полный запуск на 5B здесь
не измерялся: начинай с этих ограничений и смотри время каждого среза в summary.json.
Для всех 26 021 пользователей добавь `--max-users 0`.

Кеш привязан к версии/коду агрегатора, пути, размеру и времени изменения файла, а также
к срезу. При изменении локальных данных он пересчитывается. Он не содержит будущих
событий для соответствующего среза. Если файл был специально подменён с сохранением
его размера и mtime, очисти кеш или укажи новую директорию.

Результаты не перезаписываются: для нового опыта меняй `--out`. Завершённый срез также
сохраняется в `checkpoint_<cutoff>.json`; если следующий упадёт, уже полученные результаты
останутся доступны. Это контрольные файлы, а не автоматическое продолжение запуска.

## Что сравнивается

| Источник | Сигнал |
|---|---|
| `pop_all` | Все прошлые лайки |
| `pop30`, `pop7`, `pop2` | Последние 30, 7 и 2 дня |
| `decay7`, `decay30` | Экспоненциальное затухание с постоянной времени 7 и 30 дней |
| `growth7` | Рост к предыдущей неделе: `log((pop7+2)/(prev7+2)) × log1p(recent_users)` |
| `momentum7` | Абсолютный прирост `pop7 − prev7` |
| `artist_pop` | Затухающая личная склонность к артисту × популярность его треков |
| `artist_trend` | Та же склонность × свежая популярность трека × ограниченный недельный рост |
| `rrf_trends` | Объединение восьми общих источников, снова до 1000 треков |
| `rrf_personal` | Сбалансированное объединение общих и артистных источников, снова до 1000 |
| `union_oracle` | Верхняя граница для полного, более крупного объединения всех кандидатов |

`growth7` и `momentum7` требуют положительного роста и минимум **10 разных пользователей**,
лайкнувших трек за последнюю неделю; параметр `--min-support`. Окна считаются по событиям,
но порог поддержки — по разным людям, чтобы один пользователь с повторными лайками не
создавал «массовый тренд». Сглаживание +2 предотвращает деление на ноль. Это явные исходные
параметры эксперимента, не найденные оптимумы.

Рост и свежесть различаются: `decay7` усиливает недавние события, `growth7` сравнивает
два периода. Семидневная постоянная времени в `exp(-age/7)` — не период полураспада.
Популярность отражает также работу существующих рекомендаций и доступность треков:
рост счётчика сам по себе не доказывает органический спрос или причинный эффект.

В артистных источниках сохраняются все авторские связи. Профиль пользователя строится
по уникальным прошлым трекам с последним временем лайка, за 180 дней, с затуханием 60 дней.
Топ-5 артистов выбирается только из прошлого. Каталог кандидатов ограничен общей, свежей
и растущей популярностью (номинальные доли 60/20/20, после дедупликации остаток дополняется
свежими). Это вычислительное ограничение, а не проверка всего каталога артиста. Оно может
пропустить полезный хвост. Будущие лайки в каталог и профиль не попадают.

Для `rrf_personal` сначала отдельно объединяются общие источники и два артистных,
затем две семьи получают равный вес. Иначе восемь похожих вариантов популярности просто
переголосуют персональный источник. RRF — проверочная эвристика; CatBoost позже сможет
использовать сами скоры и признаки пары.

## Что получим и как решим следующий шаг

Открой `eda_results/candidate_benchmark_v1/report.html`. Там есть:

- сравнения Recall@100 и полноты кандидатов при одинаковом предельном бюджете;
- отдельные графики свежести, роста и персональных источников;
- выигрыш относительно общей популярности с парным бутстрэпом;
- полные 100 целей, неполные цели, пользователи без прошлых лайков;
- дополнительные попадания артистов за пределами общего объединения;
- примеры растущих треков с исходными счётчиками для проверки здравого смысла;
- размер каждого фактического пула: свежие/артистные списки могут быть короче лимита.

Нас интересуют источники, которые дают **новые попадания**, а не только побеждают по
отдельности. Но прирост полного объединения имеет больший бюджет. Поэтому отдельно
смотрим `rrf_personal` при прежнем лимите 1000. `union_oracle` не выдаёт готовый топ-100,
и для него намеренно не показан Recall готовой выдачи.

Основная оценка использует следующие 100 событий лайка; ранее лайкнутые треки не
исключаются навсегда. Повторы в цели сводятся к множеству согласно приложенной метрике.
Проблема неполного будущего остаётся: active/full100 — диагностические группы, а не
доказательство соответствия скрытому тесту. Полные пользователи более активны.
Абсолютный Recall разных срезов не сравниваем как результат на одной и той же задаче.

Интервалы после множества сравнений — ориентир, не подтверждающий статистический тест.
Не выбираем источник по единственному небольшому выигрышу одного среза. Эти периоды
относятся к разработке; незатронутый финальный аудит понадобится отдельно.

## Прослушивания — опционально, без нового скачивания

Если **`data/5b/listens.parquet` уже есть**, можно сразу добавить:

```bash
python tools/benchmark_candidates.py \
  --data data/5b --out eda_results/candidate_benchmark_with_listens_v1 \
  --with-listens --listen-users 1000
```

Прослушивания исследуются на последнем срезе и одной и той же подвыборке до 1000 UID.
Используется 90-дневная история, дослушивания >50%, повторные проигрывания не клипируются.
Смотрим их Recall@100, полноту пула до 1000 и новые попадания сверх trend-RRF.
Фильтр по пользователям ограничивает сохраняемые данные, но не гарантирует небольшой
физический объём чтения файла. При отсутствии файла шаг пропускается, основные результаты
сохраняются; код ничего не скачивает автоматически.

Если сначала провёл основной запуск, не обязательно повторять его ради прослушиваний:

```bash
python tools/explore_trends.py listens \
  --data data/5b --users input/test_users.csv \
  --out eda_results/listens_only_v1 --cutoffs 23408001 --listen-users 1000
```

Этот отдельный CLI-запуск проверяет слушательский источник без сопоставления с trend-RRF.
Число среза возьми из своего summary.json; оно приведено для текущего публичного конца.
Для сравнения со сохранённым пулом без пересчёта основных экспериментов:

```python
from pathlib import Path
import json, sys
sys.path.insert(0, 'tools')
import explore_trends as core
saved = json.loads(Path('eda_results/candidate_benchmark_v1/summary.json').read_text())
snap = max(saved['snapshots'], key=lambda s: s['cutoff'])
ctx = core.load_context('data/5b', 'input/test_users.csv', max_users=saved['users'], seed=saved['seed'])
assert ctx.user_sha256 == saved['user_file_sha256']
reference = core.fuse(list(snap['source_lists'].values()), saved['parameters']['budget'])
core.run_listens(ctx, snap['cutoff'], 'eda_results/listens_only_v1', 1000, reference)
```

Не изменяй `seed`, файл пользователей или правило их выборки между сравнением. Здесь
benchmark по умолчанию использует детерминированную подвыборку, поэтому восстанавливаем
её тем же способом. Для исходного `--max-users 0` сохранённое число равно всему списку.

## Результаты для передачи

После основного CLI-запуска пришли **`all_experiments_for_review.zip`** из папки результата.
Он включает и опциональный слушательский раздел, если тот выполнен. Либо закоммить
HTML/JSON/CSV/SVG из папки результата. Кеши, модельные файлы и исходные события не включены.

Старый небольшой блок 01 не обязателен. Все его варианты входят в новый пакет.
Нейросетевые кандидаты/аудиоэмбеддинги и CatBoost не забыты: они остаются следующими
источниками и ранжированием. Этот запуск использует уже имеющиеся лайки/артистов, чтобы
выбрать полезные направления до более тяжёлых вычислений.

## Проверки

```bash
python -m unittest discover -s tests -p test_candidate_benchmark.py
```

Четыре теста покрывают пересчёт кеша при изменении файла и инвариантность к будущим событиям,
два среза с артистами и выдачей отчётов, пределы метрик/кандидатов, слушательскую историю
фиксированный бюджет объединения и итоговый CLI-архив при отсутствии опционального listens. Это синтетические проверки; качество/скорость
полных данных должен установить локальный запуск. Репозиторий ассистент не изменяет.
