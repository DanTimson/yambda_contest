# CatBoost на кандидатах из benchmark

Патч добавляет новый запуск и тесты. Старые исходники, результаты и gitignore не меняет.
Он использует уже имеющиеся `tools/benchmark_candidates.py`, `explore_trends.py` и
`explore_yambda.py`; автоматического скачивания данных нет.

## Зачем сейчас

На полном benchmark свежая популярность устойчиво выигрывает у исторической, а
персональное объединение с артистами — у общих источников. На последнем срезе его
Recall@100 по активным пользователям = 0.057742, при полноте того же пула 1000 = 0.192435.
Полное объединение имеет полноту 0.293633 при среднем размере около 3042 кандидатов.
Это повод сравнить ранжирование и два бюджета, а не считать все виды трендов одинаково
полезными: относительный рост слаб самостоятельно, равновесный global RRF уступает
лучшему одиночному источнику по полноте на всех четырёх срезах.

## Применение

Сохрани `yambda_ranker_v1.patch` в корень своего репозитория. Из активированного окружения:

```bash
cd "$HOME/yambda_contest" &&
git apply --check yambda_ranker_v1.patch &&
git apply yambda_ranker_v1.patch &&
uv pip install -e . &&
python -m unittest discover -s tests -p test_candidate_ranker.py
```

Это команды для выполнения пользователем. Ассистент не вносит изменения в репозиторий.
Если git apply --check сообщает о конфликте, не применяй принудительно: пришли вывод.

## Рекомендуемый запуск

```bash
cd "$HOME/yambda_contest" &&
python tools/train_candidate_ranker.py \
  --data data/5b \
  --users input/test_users.csv \
  --out eda_results/candidate_ranker_v1 \
  --max-users 5000 \
  --train-users 1500 \
  --train-future-days 150 \
  --val-future-days 90 \
  --eval-future-days 60 30 \
  --candidate-budgets 1000 3000 \
  --iterations 100 200 400 \
  --threads 4 \
  --artist-catalog 200000 \
  --min-support 10 \
  --seed 42 \
  --cache-dir data/eda_cache
```

Здесь 5000 — воспроизводимая подвыборка тестовых UID для первой проверки ранжировщика,
а не все 26 021 пользователя. Обучение использует 1500 из них. Популяционные счётчики
считаются по полным прошлым данным. Это ограничивает стоимость первого обучения;
скорость полного файла и потребление памяти новым запуском пока не измерялись.

Нужен запас RAM и диска: максимум около 4.5 млн обучающих пар и до 15 млн пар на каждый
из трёх периодов оценки. Признаки записываются порциями в Parquet; обучение каждого
бюджета загружает его обучающую матрицу. Инференс читает порциями. Это не гарантия
фиксированного максимума памяти — CatBoost также строит внутренние представления.
На каждый бюджет модель учится один раз до 400 деревьев; варианты 100/200/400 проверяются
по префиксам одной модели, без трёх независимых обучений.

## Временные границы

- История каждого снимка: строго раньше его cutoff.
- Train: срез за 150 дней до конца, метки только до validation за 90 дней до конца.
- Validation: срез за 90 дней, метки только до первого периода проверки за 60 дней.
- Проверки разработки: срезы за 60 и 30 дней, метки до наблюдаемого конца журнала.
- Число деревьев и бюджет выбираются на validation; поздние периоды не переопределяют
  выбранную модель. Для диагностического сравнения каждый бюджет использует собственное
  лучшее число деревьев с validation.

Цель согласована с последним EDA: первые 100 событий лайка, сравнение уникальных item_ids;
старые лайки не исключаются навсегда. Метки train/validation обрезаются на границе следующего
периода, чтобы не использовать будущее при обучении/выборе модели. Это оставляет неполные
цели и смещение по длине наблюдения; проблема не объявляется решённой. Отдельно выводятся
оценки all/active/full100. Active — пользователи с хотя бы одной наблюдаемой целью;
full100 — с полными 100 событиями, они могут иметь меньше 100 различных треков.

Уже изученные периоды являются разработкой, не независимым финальным тестом.
Абсолютные метрики новой 5000-user выборки нельзя напрямую сравнивать с полным benchmark.
Сравнивай CatBoost и RRF внутри этого запуска на одной группе и одинаковом наборе кандидатов.

## Кандидаты и признаки

Сохраняются восемь общих источников и два источника артистов из benchmark. Полные их
объединения ранжируются по двум семействам RRF; только потом применяется лимит 3000.
Для бюджета 1000 берётся префикс того же порядка. В отличие от старого `rrf_personal`,
семейства здесь не обрезаются до 1000 перед финальным объединением: это позволяет проверить
более крупный пул. Поэтому прежнее число Recall не считается точным воспроизведённым
базовым результатом; RRF пересчитывается на тех же кандидатах внутри нового опыта.

В CatBoost подаются 32 скалярных признака:

- логарифмы популярности и затухающих счётчиков на разных масштабах;
- относительный/абсолютный рост и число недавних пользователей;
- время с первого наблюдаемого лайка (не дата релиза);
- активность и свежесть истории пользователя;
- был ли уже лайк этого трека, сколько раз и как давно;
- позиции в каждом общем/артистном источнике и в объединениях, число источников.

UID/item_id не являются признаками. Позитивы не добавляются в кандидаты по знанию ответа.
Негативы берутся из того же кандидатного распределения. Наблюдаемые пользователи без
меток пропускаются при обучении как неопределённые; их нулевые оценки сохраняются в
all-метрике. Пользователи с метками, не попавшими в кандидаты, не удаляются как «трудные».
Вес строки — 1 / число различных целевых треков пользователя; это приближение к
макроусреднению, не точная оптимизация Recall. Выбор делается по самому Recall@100.

## Выходные файлы

- `report.html`, `summary.json`, таблицы и графики — результаты для разбора;
- `eda_for_review.zip` — компактный архив для передачи;
- `model_<budget>.cbm`, `selected_model.cbm` — модели;
- `pairs/*.parquet` — сохранённые признаки/метки для анализа и дальнейших запусков;
- `pairs/*.json` — метаданные, цели и базовые показатели каждого снимка.

Архив для передачи не включает модели и большие таблицы пар. Существующий gitignore
исключает Parquet/CBM, но разрешает JSON/HTML/CSV/SVG. Метаданные с целями не содержат
признаков скрытого теста — только открытые временные окна для разработки.

Четыре автоматических теста используют синтетические данные: метрика, строгие временные
границы и неизменность признаков при добавлении будущих событий, весь цикл обучения/выбора,
а также корректное объединение top-100 пользователя, разбитого между пакетами Arrow.
Качество на Yambda этот тест не устанавливает.
